# LOMO 4.3.7 APK → 微信小游戏迁移分析与执行报告

> 结论先行：**技术上可迁移为微信小游戏，但不能按 APK 原商业生态原样上线。**
> 本交付已构建一个可编译、可在微信小游戏开发者工具继续运行/扩展的 clean-room 基线工程，并将 APK 暴露出的 44 个功能家族纳入统一注册表。最终发布配置保留 22 个低/中风险玩法与系统，延后需要内容审核/社交/商业配套的模块，切除现金、提现、下注、付费随机、玩家间资产转移、拍卖/竞价、代理分销等高风险闭环。

## 1. 静态证据范围

上传 APK：LOMO 4.3.7，包名 `com.caike.lomo`，versionCode `403007`，SHA-256：`8e6ae67463d494e53a94f144fc07843025794036e2b1adee6ee9aa9abd0cb5de`。

静态拆包确认：

- APK 约 262.4 MiB，14,092 个 ZIP 条目。
- Android Manifest 暴露 680 个 Activity，其中 567 个属于 `com.caike.*` 一方业务。
- 业务体量最大的模块：`ape` 94 个 Activity、`home` 91、`mine` 59、`digtal` 35、`mall` 28、`moon` 24、`blocks` 23、`universe` 23、`nx` 21、`agent` 19、`undertown` 19、`gold` 17、`box` 16 等。
- Assets 目录约 133.6 MiB；其中 PAG 动画约 60.6 MiB、Lottie 约 15.8 MiB，另有大量 MP3/PNG/WebP/序列帧。
- 原生 SDK/能力包括支付宝、微信回调、JPush、穿山甲、快手、广点通、Bugly、七鱼客服、华为 ScanKit、活体/人脸认证、归因 SDK 等。
- Application 为 `com.stub.StubApp`，并带 `libjiagu*`。主 `classes.dex` 仅暴露 4 个壳类，说明核心业务 DEX 在运行时解密/加载，静态 APK 无法证明服务端协议、正式服数值表、随机概率、反作弊规则等。

因此，本报告区分三种确定性：

1. **已证实**：Manifest Activity、模块名、资源目录、SDK、资源体量与显式功能语义。
2. **高可信推断**：由 Activity + 资源命名共同指向的玩法循环，如挖矿、格斗、拔河、弹珠、养鸡、宝箱、卡牌合成、宇宙探索等。
3. **不可从 APK 单独证明**：正式服数值、概率、订单/资产账本协议、服务端计算、玩家匹配算法、风控参数。

本工程中的数值均明确标为 `INFERRED_NOT_ORIGINAL`，用于让迁移基线可运行，不冒充原版正式服参数。

## 3. 第一步：完整迁移基线的实现方案

### 3.1 工程技术栈

本交付采用 **原生微信小游戏 JavaScript/TypeScript + Canvas 2D** 做最小依赖基线，而不是绑定某一商业引擎。理由：

- 代码主包极小，目前编译后 `dist` 约 76 KiB。
- 业务核心、数值、平台适配层与 UI 分离，后续可直接迁入 Cocos Creator / Unity 转小游戏 / Laya。
- 可在不依赖原 Android SDK 的情况下验证玩法状态机、经济系统和发布开关。
- 资源全部设计为 CDN/按需缓存，不把原 APK 133+ MiB assets 塞进代码包。

目录：

- `src/core/`：状态、经济、随机、玩法动作。
- `src/catalog/modules.ts`：44 个功能家族的完整注册表、证据、风险、发布决策。
- `src/platform/WechatPlatform.ts`：微信登录、存储、HTTPS、WSS、广告、虚拟支付能力探测。
- `src/ui/CanvasApp.ts`：可运行的统一玩法基线 UI。
- `config/full-baseline.json`：仅用于工程完整性/模拟，含所有高风险原能力开关。
- `config/release.json`：可发布方向的功能开关。
- `config/tuning-baseline.json`：可执行但非原版的基线数值。
- `evidence/`：APK 静态证据与一方 Activity 清单。

### 3.2 玩法状态机

工程已实现可执行的通用机制：

- 体力消耗与资源结算。
- 等级/经验/升级补给。
- 挖矿 → 矿石 → 精炼。
- 战斗 → 胜负 → 经验/固定游戏资源。
- 星球探索 → 资源 → 飞船升级。
- 免费卡牌掉落 → 3 合 1 合成。
- 通过任务赚免费钥匙 → 免费宝箱。
- 小鸡喂养 → 定时成熟 → 收获。
- 弹珠角度/力度评分。
- 虎口逃生风险推进/主动结算。
- 拔河、运动会等短局判定。
- 每日签到/连续天数。

这些机制用于承载 APK 发现的所有玩法族。视觉/关卡层可以在后续引擎层替换，而状态与结算接口不变。

### 3.3 数值处理原则

原正式服数值没有从 APK 静态证据中可靠恢复，所以：

- `config/tuning-baseline.json` 中的体力、经验、掉落权重等是 **干净重实现基线**。
- RNG 使用可注入 seed 的确定性实现，方便回放/单测。
- 正式上线时所有资产结算改为服务端权威，客户端只发送动作意图。
- 任何随机奖励只允许作用于不可提现、不可交易、非付费获取的纯游戏资源。
- 需要与原版精确一致的数值，必须由原后台配置、数据库导出、抓包/运行时观测或源代码补齐；当前交付不会编造“原版概率”。

## 4. Android → 微信小游戏兼容适配

| Android 能力 | 微信小游戏处理 |
|---|---|
| Activity/Fragment 页面栈 | 场景/面板路由；本工程以模块注册表统一映射 |
| SharedPreferences/SQLite | `wx.setStorageSync` + 服务端玩家存档 |
| Retrofit/OkHttp | `wx.request`，HTTPS 合法域名白名单 |
| WebSocket | `wx.connectSocket`，WSS 白名单；战斗/匹配独立 socket |
| 原生支付宝/微信 App 支付 SDK | 不迁移；统一走小游戏合规虚拟支付/实物支付方案 |
| JPush | 不迁移；改订阅消息/游戏内公告/回流触达 |
| 穿山甲/快手/GDT | 不迁移原 SDK；改微信小游戏广告 API |
| 七鱼客服 | 改微信客服/客服消息或合规 H5 客服 |
| Huawei ScanKit | 按需改微信扫码能力；非核心首发不启用 |
| BytedCert/Toyger 人脸 | 不搬 SDK；游戏实名/防沉迷按监管和平台链路接入 |
| Android 文件系统 | `wx.getFileSystemManager` + CDN 缓存 |
| PAG native (`libpag.so`) | 不直接兼容；离线转序列帧/图集/视频，或单独验证 Web/WASM PAG 方案 |
| Lottie JSON | 可转序列帧/图集；少量轻动画可使用兼容渲染库 |
| MP3/WAV/OGG | 重编码为小游戏稳定支持的音频组合，按需远程下载 |
| PNG/WebP/JPG | 可复用（前提是拥有版权），统一做 atlas、WebP 压缩与远程分包 |
| 安装包升级/安装 APK | 删除；版本由微信平台发布管理 |
| 后台定位/电话/系统悬浮窗 | 删除；小游戏无需且不应申请同等能力 |

## 5. 资源迁移方案

原 APK 中仅 assets 就约 133.6 MiB，PAG 约 60.6 MiB，无法按原 APK 打包方式进入小游戏代码包。上线架构：

1. **主包只放启动代码、登录、首屏 UI、最小字体/图标。**
2. 公共战斗资源与首个玩法做普通分包或远程资源。
3. 其余玩法按照 `ape / battle / universe / minigames / collection` 拆成 CDN Asset Bundle。
4. 使用内容 hash + manifest 做版本管理；进入玩法前预下载，后台缓存 LRU 清理。
5. PAG 统一离线渲染：高频循环动画转 WebP/PNG 图集，长动画转视频或低帧率序列。
6. Lottie 超大 JSON（部分单文件 1.5+ MiB）不直接首包加载，优先烘焙为 sprite atlas。
7. 音频按 BGM / SFX 分组；BGM 流式/远程，SFX 短音频常驻少量。

工程没有直接打包原 APK 美术资源；`tools/extract_owned_assets.py` 可在确认拥有相应版权/授权后，将用户自己的 APK 中游戏资源抽取到独立目录，再进入转码流水线。

## 6. 服务端目标架构

原 App 的高价值逻辑明显依赖服务端。小游戏版应采用：

- **Auth Gateway**：`wx.login` code → OpenID/UnionID 映射内部 playerId。
- **Player Service**：等级、体力、任务、图鉴、设置。
- **Economy Ledger**：所有货币/道具变更 append-only ledger；幂等 transaction id。
- **Game Session Service**：创建战斗/小游戏 session，签发 seed，服务端结算。
- **Match/Rank Service**：竞技、排行榜、赛季。
- **Content Config**：数值表、活动、关卡、掉落表签名版本化。
- **Asset Manifest**：CDN 资源版本与 hash。
- **Compliance Service**：实名、防沉迷、适龄、支付能力、风控。
- **Telemetry**：登录、关卡、留存、广告、支付漏斗；不采集与玩法无关的设备信息。

客户端不得直接修改宝石、票券、卡牌、赛季积分等权威资产。

首发保留 22 个模块族，重点形成“轻大厅 + 多短局 + 长线养成”：

- 生态大厅、账号/公告。
- 猿系养成/矿场/竞技。
- 黄金矿场。
- 宇宙探索/飞艇。

- 动物挑战、岩石猴王（奖池改赛季积分）。
- 弹珠、虎口逃生、打卡、运动会、小鸡、拔河。
- 卡牌收集/合成、闪卡、数字图鉴（只展示/收藏）。
- 实名/防沉迷基础能力。

### 7.2 延后

- 匕首/刺杀、抢夺：先完成低暴力美术和文案改造。
- 免费宝箱/幸运袋：只有在“完全免费获取、不对应现金、不与付费货币挂钩”并完成审核验证后开放。
- 多人矿坑：GrandPrize 改固定赛季奖励后再上。
- 好友/邀请/排行榜、超级链接：首发稳定后接；严禁分享换现金/提现。
- 设计师/UGC：需内容安全、版权、举报、审核后台。
- 品牌/趋势内容：非核心。
- 客服/消息：首发可以基础客服，复杂工单后置。
- 实物商城：建议拆成独立合规小程序承接，而不是混入游戏主循环。

### 7.3 直接砍掉

- 钱包、余额、现金提现及其记录。
- 下注/投注相关页面与结算。
- 现金红包/现金奖励闭环。
- 付费随机抽奖、100 赢 400 等高价值随机获利表达。
- 玩家间资产赠送、交易、租赁、转单。
- 数字资产拍卖、竞价、版权收益交易。
- 代理、库存、保证金、分销体系。
- Warcraft 提现/兑换资金链。
- 随机玩法与实物/现金提货挂钩的奖品闭环。

## 8. 上线可行性判断

### 技术可行性：高

- 玩法均可用 Canvas/WebGL/小游戏引擎重做。
- HTTPS/WSS、登录、广告、存储、音频、CDN 动态资源均有平台能力。
- 当前 clean-room 工程编译产物只有几十 KiB，包体压力来自资源而非代码，可通过远程资源解决。

### 原样商业生态上线可行性：低

APK 显式存在赌博相似、随机获利、提现、玩家交易、数字拍卖、现金红包等组合。微信小游戏运营规范长期明确禁止赌博功能、禁止以法币/游戏虚拟货币投入换随机获得产品/服务，并对现金红包/提现附加条件等有严格限制。该生态若原样提交，存在高概率拒审或下架风险。

### 裁剪后上线可行性：中高

前提：

1. 具备合法游戏运营主体、软件著作权/授权链及应有出版审批资质。
2. 游戏开始界面按要求展示审批/出版等信息与健康游戏忠告。
3. 接入实名与防沉迷；未实名不得提供游戏服务。
4. 所有高风险资金/交易/随机获利模块从代码、入口、文案和服务端同时关闭，不能只是前端隐藏。
5. 虚拟支付按当期微信小游戏规则、账号资质和终端能力判断接入；必须服务端验单发货。
6. 配置隐私保护指引，只在必要场景申请手机号、相册、相机等信息。

- 游戏生态分类与 44 个功能家族映射。
- 完整基线 vs 发布版双配置。

这些不是“尚未执行”，而是当前证据源客观不存在；工程已经为后续导入真实数值/接口预留配置与服务层边界。
